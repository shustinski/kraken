# Пространственное чтение управляемой матрицы

Этап продолжает [нагрузочную проверку](2026-10-27-matrix-functional-load.md).
Цель — функциональная готовность, без обучения и оценки качества векторизации.
Полная эксплуатационная приёмка системы остаётся открытой.

## Реализованное поведение

`matrix_viewport` передаёт границы в `frame_cells`. Для текущего состояния
SQLite выбирает только видимые серии и активные версии по индексу
`ix_matrix_coordinates_region`. Модели вне viewport не декодируются.
Обычный полный `frame_cells` и исторический `as_of` сохраняют прежний путь;
историческое состояние не подменяется текущим индексом.

`infrastructure/filesystem/matrix_coordinates.py` строит восстанавливаемую
пространственную проекцию из текущих typed models. Используются ближайшие
валидные целочисленные координаты текущей версии или её предков. Булевы,
строковые, дробные и выходящие за размеры проекта координаты не принимаются;
поиск продолжается к предку. Циклы и отсутствующие родители не создают
вымышленных координат. Детерминированный frame UUID не используется вместо
реальных координат, поэтому старые проекты с другими идентификаторами также
поддерживаются. Для дублирующихся legacy-серий одного кадра сохраняется тот же
победитель, что и при полном чтении, до фильтрации видимой области.

Проекция хранит только текущие координаты и ссылки на модели. Она не содержит
blob или отдельную историю проекта. При записи project/series/version кэш
инвалидируется в той же SQLite-транзакции. Несовпадение checkpoint также
вызывает восстановление, включая записи прежними клиентами. Удаление самой
таблицы корректно сбрасывает её отметку готовности при открытии схемы.

Тёплое чтение использует один SQLite snapshot для координат и соответствующих
series/version JSON. Устаревший кэш перестраивается атомарно после получения
writer slot и повторной проверки состояния. Неудачная перестройка откатывается;
следующий запрос восстанавливает кэш. Два одновременных читателя не видят
частично заполненную таблицу. Это гарантия данного запроса проекции, не
утверждение о глобальном snapshot всех операций Hub/Server.

Для внешнего каталога пустой viewport не равнозначен отсутствию всех
материализованных кадров: отдельная индексированная проверка сохраняет прежнее
правило fallback. Иначе каталог мог бы неожиданно показывать внешние файлы
при наличии управляемых версий вне видимой области.

## Реальный корпус и измерения

Тот же проект `3940ae7b-8ab8-4a98-8730-0448ca56b857`, 5498 пар JPEG/CIF,
сетка 100 × 55. Viewport 10 × 10, оба представления. Каждая из 100 ячеек
сверена по координатам и SHA с исходным manifest; обзор сохраняет 5498 кадров
в 91 агрегате. Исходники не изменялись, обучение не запускалось.

Первоначальное чтение и проверка канонического журнала всё ещё требуют
времени; профиль теперь показывает преимущественно повторные проверки

доказывают физическую смежность изображений.

SQLite-файл после добавления проекции: 99 147 776 байт против ранее измеренных
94 167 040. В пространственном кэше 10 996 строк (два представления × 5498).
`EXPLAIN QUERY PLAN` подтверждает поиск по covering index с ограничением
project/layer/representation и диапазоном y; затем применяется диапазон x.

Отдельный процесс выполнил 100 переходов по разным областям проекта,
сверив SHA всех возвращённых ячеек: `viewport-endurance/report.json`, passed.
RSS после первой итерации 207 990 784, после сотой 215 007 232, максимум
после принудительной сборки мусора на итерациях 215 035 904 байт; OS peak
223 354 880. Медиана повторных запросов 0,830 s при параллельном общем тестовом
прогоне/сборке. Это ограниченная серия metadata-запросов без GUI/миниатюр/Agent,
не доказательство отсутствия утечек при многосуточной работе.

проверку её использования в непустом установленном интерфейсе надо выполнить
отдельно. SCM service/reboot, clean OS/Linux и production update также открыты.

Все 2654 закреплённых файла остались неизменными и после сборки/установочных
проверок. Изменения аудиторской Markdown-документации в этот source pin не входят.

Полная матрица для очень больших viewport и обзора по-прежнему возвращает
пропорциональное число моделей. Сканирование metadata журнала, нагрузка на
внешних каталогах, несколько слоёв, конкурентные правки, удалённый сервер,
память при долгой работе и installed UI E2E требуют последующих проверок.
Тёплый индекс ускоряет управляемую матрицу, но не является доказательством
завершения всех требований производственной готовности.

# Проверка паритета локальных и серверных проектов

Дата: 29 октября 2026 года.

**Полный паритет пока не достигнут.** Проверены все публичные методы
`EmbeddedProjectService` и `RemoteServerProjectService`, маршрутизация
`DualCatalogService`, вызовы из Qt и соответствующие серверные маршруты.
У каждого сервиса по 146 публичных методов; 124 имени общие, по 22 имени есть
только с одной стороны. Количество методов не доказывает равенство поведения.

Полный перечень, сигнатуры и расположение реализаций:
[catalog-operations.json](2026-10-29-catalog-operations.json).
Повторная инвентаризация: `.venv\Scripts\python.exe tools/audit_catalog_operations.py`.
Скрипт также проверяет обязательный контракт и завершается с ошибкой при
пропущенных операциях, несовместимой форме вызова или общей операции вне контракта.

Общий прикладной контракт, порты хранилища, реестр команд и границы Qt описаны в
[ADR-0002](../architecture/adr/0002-shared-project-application.md).

## Разрывы, исправленные при проверке

| Операция | Исправление |
|---|---|
| Удаление слоя | Добавлены клиент, API и серверный обработчик; проверяются имя, права, ревизия и активные задания; поддерживаются откат файлов и повтор запроса. |
| Повтор задания после потери состояния | Добавлены клиент и API `/jobs/{job_id}/retry`, используется общий `RetryPluginJobHandler`; Hub не запускает локальный Agent для серверного повтора. |
| Импорт в существующее представление | Добавлены серверные планирование и импорт. Локальный и серверный импорт используют общий обработчик `application/managed_import.py`. Сервер проверяет контрольные суммы файлов, полученные при планировании. |
| Планирование импорта | Удалён принудительный локальный обход для серверного проекта: серверный путь сканируется сервером. |
| Отдельное изменение порядка слоя | Добавлен клиент к существующему `/layers/{layer_id}/reorder`. |
| Доступ к версии и исходному файлу артефакта | Добавлены `get_artifact_version` и `artifact_source_path` в серверный клиент. |
| Чтение blob по SHA-256 | Серверный клиент теперь принимает digest, который используют локальный каталог и UI; сохранена совместимость с прежними ссылками по ID версии. Размер и digest скачанного содержимого проверяются. |
| История | Серверный клиент применяет `as_of` и `event_types`; фасад передаёт оба параметра. |
| Прошлые состояния проекта, слоёв и представлений | `as_of` проходит через клиент, фасад и API до существующих временных проекций хранилища. |
| Создание проекта по шаблону слоёв | `layer_template` больше не игнорируется серверным путём. Создание слоёв использует отдельные ключи повторяемости. |
| Создание слоя с заданным ID | `layer_id` больше не отбрасывается серверным клиентом и передаётся команде приложения. |
| Матрица | Выравнены `include_missing` и выбор представлений при отсутствии списка; `frame_cells` и `frame_management_states` используют общий `FrameQueryService`. HTTP передаёт `as_of` и `bounds`, включая исторические состояния проверки и атрибуцию. |
| Выдача работ | Локальный метод принимает явный `companion_representations`, как серверный. |
| Общая маршрутизация | Явные методы `ProjectApplication` передают операции выбранному адаптеру. Удалён `__getattr__`; известный серверный проект при отключении сервера не перенаправляется в локальный каталог. |
| Переименование | Общий обработчик координирует изменение метаданных и порт перемещения каталогов; предусмотрены откат, повтор и блокировка вместе с удалением. |
| Чтение результата сшивки | Общий `stitch_block` заменяет доступ Qt к приватному backend и выбор файлового/HTTP-чтения в диалоге. |
| Агрегация отчётов | Правила статистики перенесены в `application/reporting.py`; инфраструктура отвечает за экспорт файлов. |
| Пользовательские команды | Общие DTO, реестр обработчиков и типизированный результат доступны через прямой вызов и `/projects/{project_id}/commands`. Сервер формирует контекст из сессии, запрещает внутренние команды исполнителя и подмену проекта. |

У всех 124 общих методов теперь совпадает набор имён параметров. Это проверяет
контракт вызова, но не означает, что проверены все комбинации значений и прав.

## Остающиеся функциональные разрывы

Эти операции нельзя считать реализованными в обоих каталогах только потому,
что на другой стороне есть похожий внутренний механизм.

| Возможность | Локальный проект | Серверный проект | Что остаётся |
|---|---|---|---|
| Резервная копия проекта | `export_backup`, `import_backup`, `attach_project` | Соответствующих методов клиента Hub нет | Общий пользовательский сценарий экспорта, восстановления и подключения с проверками прав и целостности. Административные инструменты сервера не заменяют этот контракт. |
| Проверка целостности | `scan_integrity` | Нет соответствующего вызова клиента | Серверная проверка событий/blob и единый отчёт в Hub. |
| Настройка каталогов существующего проекта | `bind_project_workspace` | Каталоги задаются конфигурацией сервера и `_ensure_server_workspace` | Серверный API настройки либо явно согласованный отдельный сценарий администратора. Параметры `source_root`/`derived_root` при серверном создании по-прежнему не выбирают корни. |
| Ручные исполнители | `create_manual_performer`, `update_performer`, `archive_performer` | Клиент умеет только читать список | Серверные команды создания, изменения и архивации с правами доступа и маршрутизацией изменений в правильный каталог. |
| История производных запусков | `begin_derived_run`, `fail_derived_run`, `publish_workspace_plugin_result`, `list_derived_runs` | Есть очередь заданий и публикации; `DualCatalogService.list_derived_runs` возвращает пустой список | Единая модель просмотра запусков и результатов. Пустой список не равнозначен поддержке этой операции. |
| Удаление проекта | Локальный `delete_project` забывает каталог/кэш и сохраняет пользовательские деревья файлов | `request_project_deletion`, `project_deletion_requests`; исполнение через административный сценарий | Разные результаты и полномочия. Простое перенаправление локального удаления на сервер нарушило бы существующий порядок удаления. |

## Разные реализации уже существующих сценариев

Ниже перечислены остальные методы, доступные только с одной стороны. Они
нужны для полноты проверки; одинаковое имя метода здесь само по себе не нужно.
При требовании единого сервисного интерфейса понадобятся адаптеры.

| Методы только локального сервиса | Реализация серверного сценария |
|---|---|
| `create_initial_account`, `login`, `resolve_session` | `register_local`, `authenticate_local`, `current_principal`: отдельные локальная и серверная сессии. |
| `import_agent_result`, `import_agent_publications` | Результаты сервера принимаются аутентифицированными маршрутами `/agent/jobs/...`; сетевые callback не должны читать локальную staging-папку Hub. |
| `dispatch_stitch`, `refresh_stitch`, `import_stitch_publication` | Серверная очередь сшивки и обработчики публикаций в `persistent_services_parts/stitch_execution.py`. |
| `tick_layer_pipeline` | Серверный обработчик конвейера и фоновое выполнение. Прямой вызов этого метода через фасад для серверного проекта пока не поддержан клиентом. |

| Методы только серверного клиента | Реализация локального сценария / назначение |
|---|---|
| `statistics` | Реализован для локальных проектов в `DualCatalogService.statistics` через `ReportService`. |
| `server_analysis_runs`, `server_analysis_run`, `server_analysis_frames`, `create_server_analysis`, `command_server_analysis` | Локальный `AnalysisRunCoordinator` и `FilesystemAnalysisStore`; UI выбирает локальный или серверный контроллер. Прямых одноимённых методов локального сервиса нет. |
| `request_server_analysis_map`, `server_analysis_map_bytes` | Локальный `LocalAnalysisMapController` и хранилище карт. |
| `run_interactive_job` | Локальный UI запускает плагин через локальный Agent; серверный путь получает desktop lease и запускает `ServerAgentWorker`. Прямой одноимённый метод локального сервиса отсутствует. |
| `remote_stitch_block` | Совместимый транспортный метод; оба адаптера предоставляют общий `stitch_block`. |
| `start_sync`, `stop_sync`, `subscribe_project`, `unsubscribe_project`, `add_wake_handler`, `add_catalog_handler`, `add_status_handler` | Сетевой механизм уведомлений, принадлежащий серверному транспорту и фасаду. |

`request_project_deletion` и `project_deletion_requests` включены в таблицу
функциональных разрывов выше. Таким образом учтены все 22 локальных и все
22 серверных несовпадающих имени.

## Проверки и пределы вывода

Добавлены сценарии импорта для обоих каталогов через настоящие обработчики
приложения, повтор импорта без новых событий, обнаружение изменения исходного
файла, серверный повтор задания, временные проекции, шаблон слоёв, чтение blob
по digest и ID версии, маршрутизация позиционных вызовов, фильтры истории,
границы кадров, аутентификация API и совпадение параметров общих методов.

Результат расширенного прогона: **336 тестов прошли, 4 пропущены,
дополнительно 4 subtest**. Пропущены проверки живого сервера/Agent и PostgreSQL:
соответствующие переменные окружения не настроены.
После усиления проверки порядка позиционных аргументов и возможности вызова
по именам повторный целевой прогон завершился успешно: 42 теста.
Ruff прошёл для новых реализаций и новых тестов. В существующем
`tests/test_remote_catalog.py` остались три прежних E731 на строках 298–300;
они присутствуют и в HEAD и не относятся к изменённому сценарию маршрутизации.

Проверки серверного фасада используют обработчики приложения и локальное
тестовое хранилище; они не заменяют интеграционный прогон против PostgreSQL.
Полный список неподдержанных сценариев выше остаётся открытым результатом
аудита. Утверждать полный функциональный паритет по этим проверкам нельзя.

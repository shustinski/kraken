## Поведение

Перед удалением исходного файла CSliser теперь сохраняет неизменяемую соседнюю
запись `.имя.csliser-remove-UUID.json`: версию схемы, исходное имя, filesystem
identity/размер/mtime и SHA-256. Запись fsync-ится **до** переименования исходника
в карантин; POSIX дополнительно синхронизирует каталог. До удаления карантина
ещё раз проверяются identity, metadata и содержимое. Если запись нельзя
надёжно создать, исходник не изменяется. Отмена действует и при хешировании.

На запись удерживается межпроцессная OS-блокировка: восстановление не
вмешивается в живую операцию. После аварийного выхода блокировка снимается
ядром ОС, запись остаётся доступной для проверки.

CLI: `CSliserCli.exe --recover-source <папка>`; параметр повторяется для
нескольких папок. Обрабатываются только непосредственные записи выбранных
папок, максимум 10000 за запуск; scan ограничен миллионом directory entries.
JSON различает `restored`, `source_unchanged`, `already_removed`, ошибки.
Некорректные/слишком большие записи, изменённый файл и занятое исходное имя
дают отказ; существующие файлы не перезаписываются.

GUI: **Действия → Восстановить файлы из карантина…**. Пользователь выбирает
папку и подтверждает действие; хеширование и восстановление выполняются
обычным фоновым Qt worker с отменой и ожиданием завершения при закрытии.
Параметры запуска окна сами по себе восстановление не запускают.

Восстановление возвращает проверенный карантин на исходное имя; удаление
не возобновляется. В прерванном cross-volume move готовая копия назначения
сохраняется: после возврата исходника возможны две одинаковые копии. Это
сообщает сохранность данных, а не успешное завершение первоначального move.
Когда удаление уже произошло и обе исходные записи отсутствуют, результат
`already_removed` **не означает**, что файл восстановлен.

Обычный успешный путь удаляет только собственную запись после завершения
операции. Записи с конфликтами и неясным исходом сохраняются для разбора.
Политика `safe_files` Kraken запрещает `:` и обратную косую черту в компонентах
пути на обеих ОС; для допустимого POSIX-имени с двоеточием проверен отказ до
любого изменения исходника. Это существующее ограничение общего контракта.

## Границы результата

Это write-ahead recovery для **source quarantine** при delete и copy-then-remove
в cross-volume move. Пока нет единого журнала всего batch, восстановления
стадий copy и регистрации same-volume move. Запись не содержит backup bytes
и не позволяет вернуть уже удалённый файл. Нет доказательства поведения при
физическом отключении питания, аппаратном отказе/лжи fsync или смене файловой
системы; Windows file fsync не объявляется directory durability SLA.
Два чтения исходных bytes перед удалением добавляют I/O; новый performance SLA
не заявляется. Враждебный процесс того же пользователя не считается sandboxed.

Native Computer Use pipe остаётся недоступным. Внутренние Qt tests и installed
self-test не заменяют обычный внешний ввод в окно, login/restart и полный
desktop/remote/installed 20-stage E2E. Эти и остальные открытые требования
Kraken сохраняются; полная производственная готовность не объявляется.

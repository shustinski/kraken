# Дизайн: окно входа Kraken Hub — доменная и локальная учётная запись

Дата: 2026-11-11
Статус: макет согласован с пользователем (визуальный компаньон, вариант A + поле «Сервер»); документ на финальном согласовании

## Цель и почему

Доменный (LDAP) вход в Kraken Server уже работает на уровне протокола
(сервер: локальная проверка → AD → JIT-аккаунт при первом входе), но в хабе
нет удобного пути: сервер задаётся в Настройках, а доменным пользователем
приходится вручную создавать «программный аккаунт». Задача: окно входа при
запуске даёт оба способа аутентификации сразу:

- **Доменная учётная запись**: адрес сервера (можно указать/поменять прямо
  в окне), логин подставлен из Windows, пароль вводится один раз и
  сохраняется в Windows-хранилище — следующие запуски подключаются к
  серверу автоматически.
- **Локальная учётная запись**: как сейчас (хранилище, логин, пароль,
  автозаполнение).

Плюс: в Kraken Admin в списке аккаунтов видно, какие аккаунты доменные
(колонка «Тип»).

## Цели / не цели

- Цели: вкладки «Доменная» / «Локальная» в окне входа; поле «Сервер» и
  статус LDAP на доменной вкладке; доменный вход с сохранением учётных
  данных в существующем механизме программных аккаунтов; автоподключение к
  серверу при следующих запусках; колонка «Тип» в списке аккаунтов
  Kraken Admin; флаг `domain_auth` в `/api/v1/health`.
- Не цели: отмена обязательной локальной сессии (это фундамент приложения:
  локальное хранилище, workspace, кэш); автозаполнение доменного пароля из
  Windows-учётных данных; новые провайдеры в каталоге аккаунтов; изменения
  GitLab/OIDC-пути; изменения серверной части аутентификации (она уже
  реализована и покрыта тестами).

## Ограничения

- Локальная сессия обязательна для старта приложения (`_login` возвращает
  `None` → выход). Доменный путь завершается только после локальной части.
- Серверный путь входа: `POST /api/v1/auth/sessions` → локальная проверка,
  затем AD, JIT-аккаунт (`DomainAuthBroker`). Хаб уже умеет ходить по нему:
  `ProjectWorkspaceService.configure_remote_local(url, username, password)`.
- Программные аккаунты: каталог в `QSettings("Kraken","KrakenHub")`
  (`accounts/catalog`) + секреты в `KeyringSecretStore`
  (Windows Credential Manager). Автоподключение при старте уже существует:
  `_connect_saved_server` берёт аккаунт по умолчанию.
- `/api/v1/health` сейчас не сообщает о доменной авторизации.
- Сервер на этой машине: `http://127.0.0.1:8080`, LDAP включится после
  появления DPAPI-файла `ldap-bind.secret` (учётная запись от ИТ) — вне
  scope данного изменения.

## Подход (рассмотренные варианты, выбранный — 4)

1. Кнопка «Войти как …» внутри локального диалога (первая итерация):
   доменный вход оставался вторым шагом после локального — отклонено
   пользователем («всё должно делаться сразу при запуске»).
2. Два блока на одном экране (макет B): доменная кнопка сверху, локальная
   форма ниже. Отклонено: всё на одном экране, доменному блоку мало места
   (нужно поле сервера + статус).
3. Две панели рядом (макет C): обе формы видны сразу, но окно заметно
   шире — отклонено.
4. **Две вкладки «Доменная учётная запись» / «Локальная» (макет A) +
   поле «Сервер» на доменной вкладке — ВЫБРАНО пользователем.** Компактно,
   одна форма за раз, место для поля сервера и статуса.

## Дизайн окна (согласованный макет)

Окно «Вход в Kraken», сверху сегментированный переключатель из двух
вкладок.

### Вкладка «Доменная учётная запись»

- **Сервер** — редактируемое поле, предзаполнено адресом из настроек
  (пусто, если не задан). Пример: `http://127.0.0.1:8080`.
- **Статус** — строка под полем сервера, три состояния:
  «доменная авторизация включена» (успешный `/health` с `domain_auth:
  true`), «доменная авторизация не включена» (сервер отвечает, но LDAP
  выключен), «сервер недоступен» (нет ответа / неверный адрес).
- **Логин** — предзаполнен текущим пользователем Windows
  (`os.environ["USERNAME"]`), редактируемый (общие рабочие станции).
- **Пароль** — поле пароля.
- **Войти** — кнопка.

### Вкладка «Локальная»

Без изменений относительно текущего окна: «Локальная сессия рабочей
станции», строка хранилища, логин, пароль, «Войти»,
«Заполнить сохранённые данные…».

### Видимость вкладки «Доменная»

Показывается, когда в локальном хранилище есть хотя бы один аккаунт
(диалог первого запуска — только создание локального аккаунта: доменный
путь требует завершённой локальной сессии). Адрес сервера на вкладке
можно указать даже если он ещё никуда не сохранён — поэтому вкладка не
зависит от текущих настроек.

## Поведение

### Доменный вход (первый раз)

1. Пользователь проверяет/правит адрес сервера; статус обновляется при
   открытии окна (таймаут ~3 с) и повторно при нажатии «Войти», если адрес
   менялся. Если статус «не включена» или «недоступен» — «Войти» сразу
   показывает ошибку, пароль не запрашивается.
2. Ввод пароля → `configure_remote_local(url, login, пароль)` →
   `POST /auth/sessions` (на сервере: локальная проверка → AD → JIT).
3. Успех: сохранить/обновить программный аккаунт (provider `local`,
   username=логин, пароль, `is_default=True`) в каталоге + keyring;
   сохранить адрес сервера в настройки (то же поле, что
   Настройки → Хранение). Если аккаунт с таким логином уже есть —
   обновить его пароль, дубликат не создавать.
4. Локальная часть: попытка авто-входа в локальный аккаунт по сохранённым
   данным (существующая Windows-верификация). Успех → старт приложения,
   сервер подключён. Нет сохранённых данных → диалог переключается на
   вкладку «Локальная» с подсказкой «Доменный вход выполнен. Завершите
   локальный вход.»
5. Ошибки: 401 → «Неверный доменный пароль» (ничего не сохраняется, можно
   повторить); 503 → detail сервера (например, «Доменная авторизация
   временно недоступна»); сеть → «Сервер недоступен».

### Следующие запуски

Локальный вход на вкладке «Локальная» (или автозаполнение) → штатный
`_connect_saved_server` молча перечитывает сохранённый программный
аккаунт (доменный логин + пароль из keyring) и подключает сервер.
Пароль повторно не вводится; при смене доменного пароля — вкладка
«Доменная» с новым паролем.

### Kraken Admin

Таблица аккаунтов: новая колонка «Тип» — «доменная» при
`auth_provider == "ldap"`, иначе «локальная» (`account_rows` уже отдаёт
`auth_provider`; LDAP-аккаунты в списке уже появляются — колонка делает
это очевидным).

## Что меняется по коду

1. **Сервер** (`kraken_server/interface/http/routes/auth.py`, `health()`):
   `status["domain_auth"] = domain_auth is not None`.
2. **Хаб, окно входа** (`kraken_hub/presentation/qt/parts/login.py`):
   переделать диалог на вкладки; доменная вкладка — поле сервера, статус,
   логин, пароль, «Войти»; локальная вкладка — текущий контент.
3. **Хаб, помощники доменного входа** (новый модуль рядом с `login.py`):
   проверка `/health` с таймаутом и перевод в статус (изолированный
   HTTP-клиент, тестируемый без Qt); сохранение/обновление программного
   аккаунта по username (в `preferences_dialog.py` такого пути нет —
   добавить функцию обновления секрета); вызов
   `configure_remote_local` и обработка ошибок.
4. **Kraken Admin** (`kraken_admin/presentation/qt/window.py`,
   `_build_accounts_tab`/`_fill_accounts`): колонка «Тип».

## Решения, принятые автором (не обсуждались с пользователем)

- Поле «Логин» редактируемое (предзаполнено из Windows) — для общих
  рабочих станций.
- Статус перепроверяется при нажатии «Войти», если адрес менялся после
  последнего запроса.
- Доменный аккаунт всегда становится аккаунтом по умолчанию.
- В диалоге первого запуска (нет локальных аккаунтов) доменная вкладка не
  показывается.
- Проверка `/health` с таймаутом ~3 с при открытии окна; недостижимость —
  не ошибка, а статус «сервер недоступен».
- Вкладка по умолчанию — **«Доменная (серверная)»** — решение пользователя.
  Следствие: существующий тестовый каркас (`tests/helpers/qt_harness.py`,
  `_sign_in` кликает первый `QDialogButtonBox` и находит элементы по
  object-name) должен быть обновлён: тесты, гоняющие локальный вход,
  явно выбирают вкладку «Локальная» (по object-name вкладки/кнопок), а не
  полагаются на порядок. Локальный путь при этом остаётся рабочим:
  если сервер недоступен, на доменной вкладке «Войти» сразу даёт ошибку
  и тест/пользователь переключается на «Локальную».
- Upsert программного аккаунта: обновляется только аккаунт с тем же
  логином и provider `local`. Если с таким логином есть только аккаунт
  provider `gitlab` — создаётся отдельный `local`-аккаунт рядом; GitLab-токен
  не затрагивается.
- `configure_remote_local` и её закреплённый тест
  (`tests/test_no_auto_registration.py`) не меняются: маппинг ошибок
  (401/503/сеть) делается в новом помощнике доменного входа.

## Тесты

- Сервер: флаг `domain_auth` в `/health` (LDAP настроен / не настроен).
- Хаб: помощники без Qt — перевод ответа health в статус (успех/выключен/
  недоступен/таймаут), сохранение/обновление аккаунта по username
  (новый, существующий с другим паролем, дефолт), маппинг ошибок
  (401/503/сеть). Qt-диалог — по существующим паттернам тестов репозитория
  (если их нет для диалогов — только помощники).
- Kraken Admin: значение «Тип» для локального и ldap-аккаунта в
  `account_rows`/заполнении таблицы (по существующим паттернам).

## Что остаётся реализатору

- Точная организация Qt-вкладок и обновление статуса (debounce/повтор при
  смене адреса) — в рамках описанного наблюдаемого поведения.
- Местоположение и сигнатуры новых помощников, тестовый каркас по паттернам
  репозитория.

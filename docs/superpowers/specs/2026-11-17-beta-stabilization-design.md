# Дизайн стабилизации Kraken до первой беты

Дата: 2026-11-17. Заказчик — владелец проекта. Режим: стабилизация существующего
функционала, новые фичи не разрабатываются. Объём и форму приёмки согласовали в
обсуждении; документ фиксирует договорённость для планирования и исполнения.

## Зачем

Kraken — система управления проектами реверс-инжиниринга ИС (Hub, Manager,
Server, Agent, Blob Gateway, плагины). Проект три недели не может выйти на
передачу тестировщикам: чинятся модули по очереди, а приёмочный критерий в
`docs/quality/stabilization-plan.md` сформулирован как полный продакшн-аудит
(~90 действий, «NOT_TESTED не остаётся»), и при этом поверх непройденной приёмки
продолжали мержиться новые фичи (вкладки проектов 09.11, LDAP/доменный вход
10–11.11, «вход любой учётной записью» 17.11). База приёмки уезжает — процесс не
сходится.

Результат, который нужен: **первая бета, отданная тестировщикам**, с надёжным
сквозным серверным потоком и полной палитрой действий внутри бета-объёма.

## Бета-поток (что должен уметь тестировщик от и до)

Создать серверный проект; добавить слои; на слое вести несколько вариантов
изображений и переключать основной; векторизовать слой в Contour (каждый слой
векторизуется отдельно); подготовить выборку Contour для NeuralImage; обучить
модель NeuralImage; выполнить бинарную сегментацию и получить новый вариант CIF;
настроить план восстановления слоя (какие слои выгружать при выдаче кадров на
проверку); выдать кадры на коррекцию серверным способом — закрепить задачу за
пользователем; пользователь под своей учётной записью выполняет её в «Моя
работа»; приёмка слоя после ручной коррекции; выгрузка статистики по проектам,
неделям/месяцам/годам с графиками по проектам и пользователям.

## Границы беты

**В бете:** Contour, NeuralImage; вход (локальный и серверный), роли и
исполнители; серверный контур PostgreSQL + Blob Gateway + агент; updater.

**Вне беты (явно, с причиной в реестре):** Karakal (приёмку ведёт другой
разработчик), сшивка (управление, вычисляемая, `layer.stitch.v1`), физические
слои и контакты, электрическая связность, Krona, CSliser, KateGB, офлайн-обмен
переносными пакетами, миграция старых поручений, Windows-служба, Hello,
технологический процесс слоя, dev-сессия, подключение проекта из локального
каталога, контроль качества (диалог дефектов — не назван заказчиком; приёмка
коррекции идёт через поручение). Доменный LDAP-вход в бете выключён
конфигурацией сервера (`domain_auth=false`); вкладка в окне входа при этом
флаге не показывается — изменения кода не требуются.

Решения «контроль качества» и «технологический процесс» вне беты — предложение
исполнителя, заказчик их подтвердил молча (согласием общего дизайна). При
возражении заказчика они возвращаются в объём, это удорожает приёмку сильнее
всего.

## Цели

1. Сквозной бета-поток проходит без ручных обходных путей на собранном
   установщике.
2. Каждое действие бета-объёма принято живым прогоном (см. «Палитра действий»).
3. Машинночитаемый гейт: нет строки `beta: true` без PASS (или явно принятого
   ограничения с подписью заказчика).
4. Передача тест-лиду: установщик + чек-лист ручной smoke-проверки.

## Нецели

- Новые пользовательские возможности.
- Полный аудит всех ~90 действий реестра (это Approach B, отклонён).
- Качество модели и электрическая приёмка реального прибора (исторически вне
  области, квитанции прогонов фиксируют это и дальше).

## Антицели

- «Зелёные» статусы без внешнего прогона (чтение `plugin.json`, opt-in тесты
  без запуска, in-process подмены вместо настоящего агента — «ложные зелёные
  зоны» из `test-gaps.md`).
- Ремонт без регрессии: каждая починка — RED→GREEN с тестом, как в D1–D20.

## Подходы (выбран A)

**A. «Бета-контур».** Флаг `beta` в реестре; гейт и отчёт готовности считаются
только по `beta: true`; заморозка фич; волны W1–W4; сходимость конечна, покрытие
не деградирует. **Выбран.**

**B. Продолжить полный аудит (~90 действий, включая Karakal/сшивку/электроприёмку).**
Максимальная дотошность, но именно он не сходился три недели: объём каждый раз
растёт, а бете это не нужно. Отклонён («нужна бета, новые фичи не нужны»).

**C. Отдать как есть, чинить по жалобам.** Текущее состояние («то один модуль,
то другой»). Отклонён.

## Механика: флаг `beta` в реестре

- В `docs/quality/registry/actions.json` у каждого действия поле `beta`
  (bool) и, для `beta: false`, `beta_out_reason` (причина: «вне объёма беты —
  <что>»). Схема `tools/quality/registry_schema.py` и проверки
  `tests/test_quality_registry.py` расширяются.
- `scripts/quality-gates.ps1`: отчёт покрытия и правило PASS→FAIL применяются
  к действиям `beta: true`; строки `beta: false` остаются в отчёте
  информационно и не блокируют гейт.
- Новые строки реестра (их сейчас нет, а бета их использует):
  - `HUB-LOGIN-TABBED` — окно входа с вкладками локальный/серверный вход;
    LDAP-вкладка скрыта при `domain_auth=false` на `/api/v1/health`;
  - `ADMIN-SERVER-BACKUP-RESTORE` — `backup-server` / `backup-verify` /
    `restore-server` на отдельной базе;
  - операции агента бета-объёма отдельными строками: `AGT-OP-VECTORIZE`
    (`frames.vectorize.v1`, interactive), `AGT-OP-DATASET-PREPARE`
    (`frames.dataset.prepare.v1`), `AGT-OP-TRAIN`
    (`dataset.model.train.v1`), `AGT-OP-BINARY-SEGMENT`
    (`frames.binary-segment.v1`/`v2`);
  - `HUB-UPDATE-SOURCE` / `HUB-CHECK-UPDATES` остаются в бете: для разблокировки
    `BLOCKED` нужен тестовый источник обновлений (манифест + установщик на
    файловой шаре или HTTP) — удалённый HTTPS-стенд не требуется: клиент
    обновлений читает манифест `urllib.urlopen` с произвольной схемой URL
    (`src/updater/client.py`), HTTPS не настоян.

## Палитра действий (форма приёмки W3)

Не один линейный сценарий, а набор живых сценариев на серверном контуре
(Server+PostgreSQL+Gateway+агент+Hub offscreen), покрывающий каждое
`beta: true` действие, включая ветки отказов:

1. **Полнота:** каждое `beta: true` действие — минимум один живой прогон.
   Живьём покрыты пока только цепочки Contour/NeuralImage и ворк-ордеры
   (`tests/test_live_server_plugin_chain.py`); остальное — новые live-сценарии
   на существующих обвязках и гейтах. Это тестовая работа, не фичи.
2. **Мультиобъектность:** 2+ слоя в проекте, каждый векторизуется отдельно;
   2+ варианта изображений на слой с переключением основного — задания и
   выгрузки берут активный вариант; слой используется, затем удаляется, проект
   остаётся читаемым; два пользователя работают одновременно (один выдаёт
   работу, другой принимает).
3. **Циклы состояний:** добавить → использовать → архивировать → восстановить →
   удалить; выдача → коррекция → приёмка → повторная выдача того же слоя.
4. **Ветки ошибок:** конфликт ревизии, отмена задания агента, неверный ввод в
   диалогах, обрыв загрузки.
5. **Учёт:** каждая строка палитры — идентифицируемый блок в
   `acceptance-matrix.md` со ссылкой на тест и доказательство.

### Правило свежести доказательств (гибрид, выбран заказчиком)

Ни одно действие бета-объёма не может иметь статус PASS на доказательстве
старше точки заморозки (даты подтверждения этого дизайна):

- всё, что проходит через серверный поток, — перепринимается живьём в
  сценариях палитры;
- то, что физически не проходит через серверный стенд (создание локального
  аккаунта, локальный бэкап проекта, настройка корней, dev-обвязка), —
  офскрин-прогон ярусами гейта, но датированный после точки заморозки.

Октябрьские и ноябрьские PASS до точки заморозки не переносятся в готовность
беты ни в одном варианте.

### Форма доказательств (решения ревью-раунда 2026-11-17)

- Живые прогоны становятся ярусом `live` в `scripts/quality-gates.ps1`: при
  настроенном `KRAKEN_LIVE_WORKER_CONFIG` ярус исполняет сценарии палитры и
  даёт статусы действий из JUnit наравне с остальными ярусами; без стенда
  ярус — PARTIAL и не участвует в выводе о готовности. Статус PASS в реестре
  без свежего прогона ярусов гейт не принимает.
- Действия, которые нельзя задрайвить скриптом (внешний вид графиков, UX
  установщика), — единственные рукописные проверки, только в W4, по
  формализованному протоколу (дата, версия сборки, исполнитель, результат по
  каждому пункту).
- Взаимодействие флагов реестра: гейт и правило «PASS→FAIL = деградация»
  считаются по `beta: true`; `mandatory` сохраняется как informational для
  будущего полного аудита; правило «NOT_TESTED требует exception_reason»
  действует на строки `beta: true`, для `beta: false` причину даёт
  `beta_out_reason` и валидация реестра на них не падает.
- Каждый сценарий палитры сам готовит своё состояние (свой проект/слой) и
  убирает за собой; разрушающие сценарии (удаление слоя, архив,
  backup/restore) не зависят от состояния, оставленного другими. «Зелёный
  дважды подряд» = два полных прогона палитры подряд без ручного вмешательства
  между ними.

## Волны работ

- **W1 — фундамент.** Флаг `beta` в схеме/реестре/гейте + классификация;
  фикс двух `test_pytorch_resolution` (обвязка: scratch-резолв не находит
  build-колёса `setuptools/wheel/pybind11` в пустом офлайн-кэше uv; проект
  официально на Python 3.14, `requires-python >=3.14`, несовместимости тут
  нет); развёртывание постоянного интеграционного стенда (PostgreSQL-тест-база,
  Server, Gateway, агент, env для гейтов) с описанием в репозитории, чтобы
  прогоны были повторяемыми.
- **W2 — ярусы.** Первой строкой — пробная сборка пакета беты (contour +
  neuralimage) в текущем окружении: риск несовместимости сборки обнаруживается
  здесь, а не в W4. Затем прогон integration/gui/stateful ярусов на стенде;
  падения — RED→GREEN с регрессиями; обновление матрицы и реестра.
- **W3 — палитра.** Реализация и прогоны живых сценариев палитры (включая
  мультиобъектность, циклы, ошибки); Karakal-цепочка из существующих live-тестов
  из гейта исключается флагом `beta`.
- **W4 — поставка.** Сборка установщика беты (contour+neuralimage, без
  Karakal/сшивки — по факту сборки проверяется, что лишнего нет), тестовый
  источник обновлений, ручная smoke-проверка 30–40 мин по чек-листу двумя
  учётными записями, передача тест-лиду.

## Критерий готовности беты

1. Гейт по `beta: true`: без FAIL; PARTIAL только с явной причиной, принятой
   заказчиком. Все доказательства PASS датированы после точки заморозки
   (правило свежести, гибрид).
2. Сквозной бета-поток зелёный дважды подряд на живом контуре (две учётные
   записи, два разных слоя).
3. Ручная smoke-проверка пройдена на собранном установщике.
4. Заморозка фич: с момента подтверждения дизайна в main мержатся только фиксы
   и приёмочная инфраструктура; нарушение заморозки требует явного решения
   заказчика.

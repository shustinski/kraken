# Любой из трёх входов достаточен для запуска Kraken Hub

Дата: 2026-11-17. Статус: одобрен (подход A выбран пользователем).

## Намерение

Сегодня успешный доменный или серверный вход не заканчивается входом в приложение:
если сохранённая локальная сессия не completes (`_try_local_autologin`: Windows Hello +
запомненный локальный пароль), диалог показывает «Вход на сервер выполнен. Завершите
локальный вход» и переключает на вкладку «Локальная» (см. скриншот пользователя).
Пользователь должен попадать в Hub по любому из трёх способов входа: доменная учётная
запись, серверная учётная запись, локальная учётная запись.

## Почему локальная сессия остаётся обязательной

Shell, владение проектами и все локальные операции работают от локального principal'а
(`run_manager_gui` требует `DesktopSession`, returned by `_login`). Отказ от локальной
сессии — архитектурная перестройка, вне рамок этой задачи (не-цель).

## Подходы, которые рассматривались

- **A. Зеркальная локальная учётка (выбран).** После успешного удалённого входа Hub сам
  выполняет локальный вход: вход по введённым данным, а при отсутствии локальной учётки
  с таким логином — её создание с тем же логином и паролем. Цена: введённый пароль
  попадает в локальное scrypt-хранилище; после удалённого входа он уже сохраняется в
  Windows Credential Manager (`upsert_program_account`), так что профиль безопасности
  практически не меняется.
- B. Скрытая учётка со случайным паролем + Credential Manager. Не дублирует доменный
  пароль, но «свой» пароль не работает на локальной вкладке — больше путаницы и механики.
- C. Работа без локальной учётки (чисто серверная сессия). Архитектурный проект, не правка входа.

## Решение

### Сервис (`EmbeddedProjectService`, `composition/parts/revoke_project_role.py`)

Новый метод `login_or_create_local(username, password) -> DesktopSession | None`:

- локальной учётки с таким логином (NOCASE) нет → создать через `accounts.create_account`
  (display_name = username), затем обычный `login()` (он же сохранит identity);
- учётка есть и пароль подходит → просто войти, ничего не создавать;
- учётка есть, пароль не подходит → вернуть `None`; существующий локальный пароль
  никогда не перезаписывается (он остаётся авторитетным);
- имя пользователя недопустимо для локального аккаунта (пробелы и т. п.) → вернуть `None`.

`DualCatalogService.login_or_create_local` делегирует локальному бэкенду (рядом с
`login`/`create_initial_account`). Метод добавляется в протокол `DesktopOperations`
(прецедент: `configure_remote_local`/`create_initial_account` уже в нём; runtime-проверка
`validate_project_operations` проверяет только `ProjectOperations`).

### Диалог (`presentation/qt/parts/login.py`, `complete_remote_sign_in`)

Порядок после успешного `configure_remote_local` (доменные и серверные вкладки — общий финал):

1. `upsert_program_account` + `save_program_server_url` — без изменений;
2. `_try_local_autologin` — без изменений (сохранённая локальная сессия имеет приоритет);
3. если не вышло — `service.login_or_create_local(введённый логин, введённый пароль)`;
   при успехе запомнить учётные данные (`_remember_credentials`, как на локальной вкладке)
   и закрыть диалог с сессией;
4. если и это `None` (такая локальная учётка уже есть с другим паролем / недопустимое имя) —
   текущее поведение: подсказка + вкладка «Локальная».

  чужой пароль → `None`, старый пароль работает; недопустимое имя → `None`;
  делегирование `DualCatalogService`.
- `tests/test_hub_login_window.py`: серверные тесты успеха (`test_server_sign_in_success_completes_session`,

  остаётся подсказка и вкладка «Локальная».

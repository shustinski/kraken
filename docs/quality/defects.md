Регрессии: `test_preflight_managed_import_counts_files_and_bytes_without_counting_other_versions`, `test_csv_preserves_nested_immutable_event_payload`, `test_statistics_calculate_and_export_buttons_use_real_history`.

### D1. Повтор создания проекта с тем же ключом идемпотентности падает

- Дополнение 2026-11-01 по независимому ревью: обнаружено удаление непустых orphan-деревьев при повторе до ProjectCreated. Воспроизведено для успешного повтора, повторной ошибки команды и изменённого имени. Исправлено: совпадающая привязка переиспользуется, отказ команды сохраняет её, изменённое имя/корни дают конфликт без удаления. Файлы обоих деревьев проверены после нового сервиса. `d1-review-red-edges`: 3 FAIL; `d1-review-green`: 37 PASS вместе с созданием и Qt. Старое описание удаления оставшейся папки ниже является историческим и заменено безопасным переиспользованием.
- Статус: исправлен 2026-10-31. До правки повтор `create_project` с ключом `project-audit` давал `FileExistsError: Папка проекта «Аудит» уже существует.`
- Проверка после правки: `tests/test_project_create_idempotency.py` — 6 тестов, код 0. Тот же ключ возвращает тот же id, после нового `EmbeddedProjectService` проект на месте, каталог `workspace-source` содержит одну папку «Аудит». Повтор после папки без журнала дописывает журнал и оставляет одну папку. Проект, записанный до стабильного id под случайным UUID, возвращается по тому же ключу, маркер в его папке сохраняется, чужой участник с тем же ключом по-прежнему получает `FileExistsError`. Обрыв после журнала дописывает одно событие `ProjectWorkspaceBoundV1`, повтор его не дублирует. Два одновременных вызова с одним ключом тоже оставляют одно такое событие: до правки второй получал `EventStreamConflict` на ревизии потока. Обрыв шаблона слоёв на втором слое при повторе дописывает остальные типы и не плодит дубли. Другой ключ с тем же именем по-прежнему получает `FileExistsError`. `tests/test_create_project_dialog_retry.py` — диалог Qt offscreen: два подтверждения одного имени после `FileExistsError` передают один ключ, смена имени даёт другой ключ, в каталоге два проекта. Рядом прошёл `tests/test_hub_embedded_service.py` (вместе с идемпотентностью и диалогом 29 тестов, код 0).
- Независимый разбор: замечания про старый случайный id, ключ `uuid4()` внутри цикла диалога, гонку общего id и незавершённые событие привязки и шаблон слоёв учтены перечисленными тестами.
- Статус сценария до исправления: FAIL (`LOCAL-PROJECT-IDEMPOTENT`).
- Шаги: создать локальный проект «Аудит» с ключом `project-audit`, сразу вызвать `create_project` с тем же ключом, именем, шириной и высотой.
- Факт: `FileExistsError: Папка проекта «Аудит» уже существует.`
- Место: `EmbeddedProjectService.create_project` создаёт каталог в `workspace_files.create_project` до выполнения команды. `CreateProjectCommand.project_id` каждый раз получает новый UUID и не восстанавливается из ключа.
- Следствие: клиент не может безопасно повторить создание. Второе имя, совпадающее с уже созданной папкой, тоже останавливается на файловой системе, даже если журнал ещё не писался.
- Ожидание: тот же ключ возвращает уже созданный проект и не пытается создать папку заново.

### D5. Роль нельзя назначить новой учётной записи, пока та сама не обратится к API

- Статус: исправлен 2026-10-31. До правки `PUT /projects/{id}/acl/{principal}/viewer` сразу после `POST /auth/accounts` давал 404 `Principal … was not found or is inactive`. Токен новой учётной записи к этому моменту не предъявлялся.
- Проверка после правки: `tests/test_registered_principal_before_session.py` — 2 теста, код 0, PostgreSQL в отдельной схеме. Владелец назначает `viewer` до использования нового токена, новый экземпляр `PostgresIdentityAclStore` читает участника, `GET` проекта этим токеном возвращает проект. Повтор того же пароля не снимает роль. Отдельный тест создаёт аккаунт мимо HTTP и проверяет, что повторный `POST /auth/accounts` с тем же паролем записывает участника и исполнителя, не предъявляя токен. Без вызова `provision_local_account` в ветке уже существующего аккаунта этот тест падал на `assert persisted is not None`. Рядом ранее прошли `tests/test_server_administration.py` и `tests/test_gitlab_oidc.py`.
- Независимый разбор: замечание про ветку повторного пароля учтено тестом выше. Каталог по-прежнему не получает роль проекта и не получает роль администратора сервера при регистрации.
- Статус сценария до исправления: FAIL (`SRV-ROLE-BEFORE-SESSION`).
- Шаги: на живом `kraken-server` с PostgreSQL зарегистрировать второго пользователя через `POST /api/v1/auth/accounts`. Сразу от имени владельца проекта вызвать `PUT /projects/{id}/acl/{principal}/viewer` с ревизией ACL.
- Факт: 404, `Principal … was not found or is inactive`.
- После `GET /api/v1/session` с токеном нового пользователя тот же `PUT` с `If-Match: 0` сохраняет роль `viewer`.
- Место: `POST /auth/accounts` создаёт только запись аккаунта. Строка участника пишется в `HybridSessionResolver`, когда токен впервые разбирается на защищённом запросе.
- Следствие: администратор не может выдать роль человеку, который зарегистрировался, но ещё не открывал API.

## Подтверждено кодом, прогон задания не выполнялся

Эти места не помечены FAIL в матрице. Их нужно исполнить, прежде чем считать дефект закрытым или опровергнутым.

- Headless-выборка Contour. `plugins/contour/src/contour/worker.py` принимает только `frames.vectorize.v1` и иначе бросает `ValueError`. Объявление `frames.dataset.prepare.v1` при этом интерактивное. Сквозное задание выборки не запускалось.
- Действия `open_path`, `open_folder`, `run_action` у Contour, NeuralImage и Krona. `run_action` всегда возвращает неуспех. Рабочий Hub этот TCP-реестр не вызывает.
- Кнопка Karakal «Отправить в Kraken» включается после `set_kraken_publish_available`. Метод `_launch_karakal`, который встраивает окно, из меню не вызывается.
- Утверждение и исполнение удаления проекта не имеют отдельного HTTP-маршрута и подкоманды `kraken-admin`. Заявка создаётся. Кто закрывает заявку из обычного клиента, по этому сеансу не проверено.
- `POST /api/v1/auth/accounts` допускает самостоятельную регистрацию обычной учётной записи. Проверка 2026-11-01 подтвердила, что это явный контракт `test_self_registered_account_is_ordinary_and_sees_only_its_projects`, а не само по себе повышение привилегий: глобальных ролей нет, чужих проектов нет, неверный пароль отвергается. PostgreSQL-регистрация и назначение viewer до сессии также прошли на отдельном тестовом кластере. Политика приглашений в репозитории не задана.
- `kraken-admin init` не запускает `KrakenBlobGateway.exe`. Процесс шлюза стартует вместе с сервером. Документ развёртывания описывает запуск шире, чем делает `init`.

# Резервная копия и восстановление Kraken Server

Команды выполняются локальным `KrakenAdmin.exe` под учётной записью,
которая может прочитать конфигурацию и её защищённые секреты. PostgreSQL
должен быть доступен. Нужны штатные `pg_dump`, `pg_restore`, `psql` совместимой
с сервером версии. Они поставляются отдельно; `--pg-bin-dir` указывает каталог
с этими программами. Без параметра используется PATH.

## Создание и проверка

```powershell
& .\KrakenAdmin.exe backup-server --config D:\Kraken\config\server.toml `
    --destination E:\Backups\Kraken-2026-10-28 `
    --pg-bin-dir 'C:\Program Files\PostgreSQL\17\bin'
& .\KrakenAdmin.exe backup-verify --backup E:\Backups\Kraken-2026-10-28
```

Для каждой копии нужен новый каталог вне хранилищ. Уже завершённая копия
не обновляется, прерванная не продолжается: её PostgreSQL snapshot уже истёк.
Наличие `manifest.json` и успешная `backup-verify` подтверждают завершённую
копию; `.incomplete.json` означает прерванное создание.

Состав копии:

- PostgreSQL: пользовательские схемы, таблицы, события, проекции, аккаунты,
  права, идемпотентность, индексы, функции, триггеры и последовательности;
- все настроенные `blob_root`, `source_root`, `derived_root`, включая пустые
  каталоги, workspace registry и ключ подписи review;
- таблицы и число строк, SHA-256/размер каждого файла, ссылки на обязательные
  managed blobs и сведения о внешних URI;
- разрешённые несекретные параметры серверной конфигурации.

Совпадающие и вложенные корни сохраняются как ссылки на один физический
набор файлов. Имена файлов внутри архива закодированы; исходная структура
описана в manifest. Ручное переименование содержимого архива не поддерживается.

KrakenAdmin удерживает общий барьер хранилища PostgreSQL и файловый барьер
Blob Gateway; занятый барьер даёт отказ с возможностью повторить команду.
Приложения этого выпуска учитывают оба барьера. Во время копирования записи
Kraken ожидают освобождения БД, а новые передачи Gateway могут вернуть 503.
Для предсказуемого времени выполнения используйте окно обслуживания и
приостановите Agent/jobs и внешние программы, пишущие непосредственно в
эти каталоги. Прямые сторонние изменения файлов не подчиняются барьерам Kraken.
Существующие исходные файлы проверяются повторно; изменение прерывает копию.

В архив не входят незавершённые `.gateway-staging/`, `.transfers/`, файловый
барьер и служебная схема `_kraken_recovery`. Они не являются принятыми
данными проекта. Исходные временные файлы команда не удаляет.

## Восстановление

Подготовьте отдельную **пустую** PostgreSQL базу. Остановите приложения,
которые могли бы начать использовать целевую базу до завершения восстановления.
Путь данных и каталог новой конфигурации должны быть новыми и различными.
URL целевой базы передаётся через переменную среды, а не аргумент командной
строки. Например, после безопасного задания переменной:

```powershell
& .\KrakenAdmin.exe restore-server --backup E:\Backups\Kraken-2026-10-28 `
    --destination D:\KrakenRecovered\data `
    --config-dir D:\KrakenRecovered\config `
    --pg-bin-dir 'C:\Program Files\PostgreSQL\17\bin' `
    --blob-gateway-executable D:\Kraken\app\KrakenBlobGateway.exe
```

Имя переменной по умолчанию — `KRAKEN_RESTORE_DATABASE_URL`; его можно
изменить через `--database-url-env`. После команды удалите переменную из
текущего окружения. Команда возвращает JSON с путём новой `server.toml`.
Запустите Kraken Server с этой конфигурацией и проверьте вход, каталог,
матрицу и скачивание файлов, прежде чем переключать пользователей.

SQL и запись о его завершении фиксируются одной транзакцией. При сбое
повторите ту же команду с `--resume`: receipt связывает архив, его SHA,
целевую базу и каталог. Команда различает rollback и уже совершённый commit.
Существующие данные иной базы или изменённые целевые файлы не перезаписываются.
Сохраняйте соседний файл `.<имя-каталога>.kraken-restore.json` до окончания
восстановления. Если сбой произошёл при публикации конфигурации и её каталог
остался незавершённым, сохраните его для диагностики и задайте **другой новый**
`--config-dir` вместе с `--resume`; данные/SQL повторно не импортируются.

Физические workspace paths в реестре переносятся в новые корни. История
событий и provenance сохраняют исходные значения; runtime разрешает старые
локаторы через `.server/recovery-roots.json`. Этот файл обязателен для
конфигурации восстановления. Повторная копия восстановленного сервера
сохраняет цепочку прежних корней. Незавершённая очистка проекта после
восстановления работает с новыми каталогами.

URL базы шифруется заново средствами текущей ОС/учётной записи. Секрет
подписи Gateway создаётся заново: ранее выданные transfer tickets истекают,
пользователь получает новые. Прежний ключ review восстанавливается из
BlobStore. Сам архив содержит базу аккаунтов и приватный ключ review;
его доступ и хранение должны соответствовать серверным данным.

## Границы переносимости

Восстанавливайте доверенный архив совместимым выпуском Kraken и PostgreSQL.
Native restore выполняет сохранённые SQL definitions; SHA проверяет
целостность, а не происхождение архива. Копия не содержит PostgreSQL cluster
roles/passwords, tablespaces, серверные сертификаты вне хранилищ, установленные
программы, модели вне корней, конфигурацию SCM, OS credentials или GitLab.
Требуемые расширения PostgreSQL должны быть установлены на целевом сервере.
Владелец восстановленных объектов — целевая PostgreSQL роль (`--no-owner`,
`--no-acl`); прикладные роли Kraken сохраняются в данных.

Внешние URI и workspace links за пределами трёх настроенных корней сохраняют
свои пути, но их байты не копируются. Их доступность нужно восстановить
отдельно. Список `external_references` относится к явно сохранённым URI и
не является полным каталогом всех внешних файловых зависимостей.
Сертификаты/CA/исполняемые файлы вне корней также остаются внешними
зависимостями; при смене машины укажите `--tls-cert-file` и `--tls-key-file`,
`--gitlab-ca-file`, `--blob-gateway-executable` по необходимости. Проверьте
адреса `blob_gateway.public_url/bind` до запуска на другой машине.
Автоматическое обновление службы, удалённая репликация, PITR/WAL и
восстановление после физического отказа диска этим протоколом не проверены.

Контракты штатных программ: [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html),
[psql](https://www.postgresql.org/docs/17/app-psql.html).
